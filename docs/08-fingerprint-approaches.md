# 指紋画像から音楽向け特徴を取り出す実装案

調査日：2026年11月7日。締切：11月10日17:00（日本時間）。状態：**提案・未採用、画像実験・実装は未実施**。端末は一般的なスマートフォン、担当者はPython初級と暫定想定しています。端末・経験の確認後に見積りを調整します。[要件定義](07-requirements.md)のF03と画像担当Bの具体化です。

## 推奨

**まずOpenCVで「模様の向きの広がり」「向きの変化」を取り出し、余裕があれば相対的な縞の細かさを加える方式を推奨します。** 指紋の認証や個人識別を作らず、撮影画像の模様を音楽に使います。学習データ・モデル配布・外部推論APIへの依存を避けられ、特徴を画像に重ねて説明できます。

最重要の判断はアルゴリズム選びより、**実際のスマホ画像で隆線（指紋の細い線）が見えるか**です。最初の半日を撮影・ROI・品質確認に使い、見えなければライブラリを増やして解決したことにしません。鮮明な画像のアップロードを代替経路として検証し、ライブ撮影が未達ならその制約を明示します。

Google技術を中核にする要件は作品全体で設計します。画像担当だけでGeminiに指紋画像を送る必要はありません。作曲・共同編曲などでのGoogle技術の役割と実行基盤をチームで決めます。

## 2. 最初の半日で試すこと

**提案時間配分：撮影60分 → ROIと目視60分 →方向場の試作・比較120分。** 開発開始条件の確認後に実施します。本書では試作を行っていません。

1. 自分または明示的な同意を得た2〜3人の指を、同じ端末・同じ指先の範囲で各3回撮影する。匿名ラベルだけを使い、画像は公開Gitに入れない。撮り直すたびに手を一度外す。
2. 明るい拡散光、背景を単純にする、指を大きく写す、手ぶれを避ける条件を試す。端末の最短撮影距離に寄りすぎず、デジタル拡大で線が復元するとは考えない。反射・強い影・斜めの指・曲面の端を避ける。
3. 原寸で隆線が見える中央部分を人が矩形で選ぶ。まず自動の指検出や背景除去を作らず、UIの枠・手動切り出しで背景や指の輪郭を除く。ROIの位置・指先の向きを揃える。
4. 原画像とROI、方向場を手元だけで見比べ、方向が隆線に沿っているか確認する。皮膚のしわ・影・背景を指紋として測っていないかを確認する。
5. 良好・暗い・ぼけ・反射・ほぼ無模様を含む入力で、特徴が出る条件と拒否する条件を決める。

**11/7中の継続ゲート（提案）**：上の各人3回のうち2回以上で「隆線が目視できるROI」と「最低2特徴が取得可能」を満たすか確認します。小規模な開発判断であり認識精度評価ではありません。満たさなければ撮影条件を1回見直し、その日のうちにアップロードを主経路にするか、指紋入力の成立が未確認であることをチームへ報告します。

権利確認済み・同意済みの鮮明な画像はアップロード経路の検証に使えます。デモ用サンプルで進む場合は常時「サンプル」と表示し、撮影画像の解析成功と見せません。ぼけから生成AIで隆線を補完して、その補完結果を本人の特徴と扱う方法は採用しません。

## 3. 推奨方式Aの処理手順

| 段階 | 具体的な作業 | 失敗時 |
| --- | --- | --- |
| 入力 | 形式・サイズを検査、画像の向きを補正、ROI選択。カメラ画像のメタデータは後段に残さない | 非対応・破損・大きすぎる入力を拒否 |
| 品質確認 | ROIの明暗分布、白飛び/黒つぶれ、局所コントラスト、勾配量、有効領域割合を確認。ぼけ指標は補助にする | 暗さ・反射・ぼけ等の理由を示して撮り直し |
| 前処理 | グレースケール化、必要なら弱い局所コントラスト補正。画像の極端な拡大・強い平滑化・過剰な強調は避ける | 線が失われる/ノイズが増える設定を棄却 |
| 方向場 | Sobel等の勾配を局所窓で集約し、構造テンソルから方向とコヒーレンスを計算 | 低勾配・低信頼の窓は欠損扱い |
| 集約 | 有効な窓から2特徴を計算。縞の周期は明確な周期がある場合だけ追加 | 有効範囲不足は抽出不可。欠損を0に置き換えない |
| 出力 | 匿名参加者ID、品質、理由、特徴値・範囲・単位・版を返す | 処理エラーを成功レスポンスにしない |
| 破棄 | 成否にかかわらず画像の一時データを解放。元画像・細部座標・特徴値をログに書かない | 保持場所を追跡できない構成は採用前に修正 |

窓サイズは固定の万能値を使わず、原画像で見える線間隔に対して選びます。処理用ROIの長辺512〜1024pxなどは開始候補にすぎません。縮小で縞が消える場合は縮小率を変え、元から解像していない場合は拡大せず失敗とします。実際に採用したROI条件、窓、前処理、ライブラリ版を抽出版と対応させます。

NFIQ 2は500 PPIの光学・インク指紋と認識性能を対象とする品質尺度です。物理スケール不明のスマホ写真に、そのまま品質保証として使う根拠にはなりません。今回は撮影経路に合わせた小規模な品質ゲートを作る提案です。[NIST：NFIQ 2](https://www.nist.gov/services-resources/software/nfiq-2)

## 4. 特徴量の意味と音楽への渡し方

以下の集約指標・音楽割当は本作品向けの設計案です。既存の指紋認証指標、本人固有の値、性格・才能の推定ではありません。

局所方向は180度周期です。方向θとθ+180度は同じ線の向きなので、単純な角度平均は使わず、2θのsin/cosで平均・差を計算します。構造テンソルの最大固有値の向きは画像勾配側なので、隆線方向を使う実装では90度回して定義を統一します。[計算法の基礎](https://docs.opencv.org/4.10.0/d4/d70/tutorial_anisotropic_image_segmentation_by_a_gst.html)

| 指標 | 定義案・範囲 | 音楽への割当例 | 制約 |
| --- | --- | --- | --- |
| 方向の広がり D（第1候補） | 有効窓の平均cos(2θ), sin(2θ)の長さをRとし、D=1−R。0〜1 | 小さい/中/大の3段階でメロディの音域を選ぶ | 方向が揃うと0に近い。輪・渦・弓の分類ではない。ROIと有効窓の変化に影響される |
| 局所方向変化 T（第2候補） | 隣り合う有効窓の方向差を180度周期の最短差δ（0〜90度）とし、平均δ/90。0〜1 | リズムの跳躍やフレーズ変化の頻度を3段階にする | 曲がりの粗い代理量。厳密な曲率・分岐数ではない。窓間隔とノイズに依存 |
| 相対縞密度 S（余裕時） | 隆線に垂直な濃淡の周期を自己相関等で推定。周期p画素から周波数1/p、またはROI幅Wに対するW/pを計算 | 音符密度を段階化 | 強い周期がある窓だけ使用。実際の本数/mmではない。撮影倍率・ROIの物理範囲・曲面に依存 |

全体の画像回転だけならDやTは理論上その影響を受けにくい設計ですが、補間・ROIずれ・有効窓の選別で結果は変わります。回転不変を保証せず実際に測ります。Sは画像のピクセル数を揃えるだけではスケール補正になりません。同じ指の同じ範囲を切り出すガイドを用意し、安定しなければ外します。

品質側のコヒーレンスCは、局所の固有値λ1≥λ2から `(λ1−λ2)/(λ1+λ2)` で求める0〜1の方向の揃い具合です。分母が小さい平坦領域は欠損にします。Cが高くても背景の直線の場合があり、指紋らしさの証明にはなりません。渦の中心等では低くなり得るため、低い窓をすべて不良指紋と断定しません。[OpenCV公式教材](https://docs.opencv.org/4.10.0/d4/d70/tutorial_anisotropic_image_segmentation_by_a_gst.html)

**コヒーレンス、ぼけ、明るさ、有効面積は品質指標として返し、音楽の個性へ直接割り当てません。** 暗く撮ると性格や曲調が変わる、という混同を避けます。音楽向け2特徴が取れなければ品質値で穴埋めしません。DとTが同じように変動しすぎる場合も情報の重複として見直します。

0〜1正規化や3段階化の境界は実測して固定し、参加者集団ごとの相対順位にはしない案を推奨します。参加者を追加しただけでAの特徴・個人モチーフが変わることを避けられます。数値差を無理に広げて全員を別人らしく見せず、同じ値になる可能性を認めます。

## 5. 再現性・品質を確認する小さな検証

| 検証 | 方法と判断 |
| --- | --- |
| 同一画像 | 同じROI・設定・版で5回処理し、特徴と品質状態が一致することを確認。浮動小数点の許容差を決める。固定パイプラインの確認であり同じ指の再撮影とは別 |
| 同じ指の再撮影 | 各人3枚を比較。3段階の音楽設定が2枚以上で一致するかを暫定目安にし、連続値のばらつきも確認。未達なら段階幅・撮影ガイドを見直す |
| 小さな回転・切り出しのずれ | 同じ画像の向き・ROIを少し変えてD/T/Sを比較。ずれの範囲と変化を記録し、耐性を過大に説明しない |
| 低品質 | 暗い・ぼけ・反射・背景だけ・無模様で失敗理由が返るか確認。特に背景だけで通過するならROI/品質ゲートを修正 |
| 参加者間 | 少人数の範囲で特徴の違いがあるかを観察。違いが出ることを本人識別精度と呼ばない。同じ特徴になるケースを許容 |
| 作曲連携 | 有効な2特徴を個人モチーフへ固定して、A+BとA+CでもAのモチーフが変わらないことを作曲担当と確認 |
| 削除 | 成功・失敗・中断の各経路で画像がファイル・ログ・例外出力・一時領域に残らないか、バックエンド担当と確認 |

しきい値の調整に使った画像とは別の撮り直し画像で最終確認します。少数例の結果を一般的な認証・再撮影安定性の保証にしません。記録は匿名の合否・処理時間・条件を中心にし、画像や特徴の実値を公開資料に載せません。

## 6. 担当間で先に固定する契約

画像担当の納品物は「抽出処理」「設定と抽出版」「取得できる特徴の説明」「成功/失敗の例と理由一覧」「処理時間と適用限界」です。FastAPIの経路やクラウド配置はバックエンド担当と合意し、先に独立した処理単位の入出力を合わせると接続しやすくなります。以下はデータ設計で、実装コードではありません。

| 出力項目 | 意味・扱い |
| --- | --- |
| participantId / requestId / revision | バックエンドから渡された匿名IDを引き継ぐ。画像から本人IDを作らない |
| source | capture / upload / sample。sampleを実測成功と表示しない |
| status / reasons | ok / low_quality / unsupported / failed。理由例：no_visible_texture、blur、glare、insufficient_roi。確率や真の指紋判定を意味しない |
| quality | 有効面積、コヒーレンス集約、露出等。名称・尺度・欠損を定義し、作曲用とは分離 |
| features | D、T、任意のS。各値の範囲・単位・取得可否を明示。欠損はnull等で表し理由を付け、0を代用しない |
| extractorVersion / preprocessingVersion | 窓・ROI・正規化条件を追跡する版。変更時は過去値と混在させない |
| durationMs | 入力読込から抽出完了まで等、計測範囲を固定 |

UI担当は撮影ガイド・切り出し・撮り直し理由・参加者表示、画像担当は品質/特徴抽出、作曲担当は固定の音楽割当、バックエンド担当は受付・制限・セッション分離・失効・画像削除を担当する案です。元画像を作曲側へ渡さない構成を推奨します。指紋の細部点座標や復元可能な画像表現は今回の契約に含めません。

## 7. 実行場所・利用条件

OpenCV 4.5.0以降はApache 2.0です。採用する正確なバージョンと依存物のライセンスを著作物一覧へ記録します。[OpenCVのライセンス](https://opencv.org/license/)

Gemini APIの無償サービスについて、確認した公式規約はセンシティブ・機密・個人情報を送信しないよう定めています。実際の契約・リージョン・課金設定によって適用条件が異なるため、有料なら自動的に指紋入力が適切になるとは判断しません。画像理解案を採る前に適用条件・保持・削除を確認し、今回は外部Vision APIへ実指紋を送る構成を推奨しません。[Gemini API追加規約](https://ai.google.dev/gemini-api/terms?authuser=00)

課金額・モデル名・無料枠は本案では固定しません。画像担当の外部推論APIを不要にしても、サーバー費用や作曲側API費用は別途発生し得ます。クラウドの一時ファイル、リバースプロキシ、エラー追跡、アクセスログにも画像・特徴を残さないことを確認し、保持/削除の実装が未確認の段階では完全削除を保証しません。
