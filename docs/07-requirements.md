# Fingerprint Symphony 要件定義

更新日：2026年11月6日。対象：11月10日17:00（日本時間）提出のハッカソン作品。

本書は企画を実装・検証へ渡すための要件案です。「企画で必須」と「MVP提案」「未決」を区別します。技術スタック、数値目標、データ保持方式はチームの承認前です。今回は文書のみ作成し、開発開始アナウンスの確認状況は[ルール](01-rules.md)に従います。

## 1. 目的と体験

指紋画像の視覚的な特徴を音楽へ変換し、音楽経験のない人も自分の音を作り、他の参加者と組み合わせて共同創作を楽しめるようにします。本人識別・認証・性格診断は目的に含めません。

中心となる体験は「Aの個人曲を聴く → A+Bを聴く → BをCに入れ替える → A+Cを聴く → 組み合わせによる変化を比べる」です。Aのモチーフが共同曲にも残ることを目指します。交流や会話が生まれる効果は未検証の仮説であり、指紋の固有性、人物識別能力、撮り直した場合の特徴・曲の安定性を保証しません。

## 2. 範囲と優先順位

| 優先度 | 対象 | 位置づけ |
| --- | --- | --- |
| Must | 撮影・アップロード、特徴抽出、5〜10秒の個人曲、2〜3人の15〜30秒共同曲、再生、参加者変更 | 企画で必須。詳細な操作・判定方法は本書のMVP案 |
| Should | 抽出特徴の可視化と音への対応説明、A+BとA+Cの比較支援 | 重要。高度な可視化を削っても入力品質・失敗理由・参加者の表示はMust |
| Later | 曲の保存・共有、複数端末での参加、リアルタイムDJ、同時ライブ編曲 | 今回の必須範囲外。保存共有は追加候補、DJは将来構想 |

**MVP提案**：同席した2〜3人が1台のスマートフォンで順番に入力し、ボタンで生成・再生成します。アカウント登録、マッチング、本人照合は行いません。1端末・ボタン方式・最大3人はスコープを絞る提案で、確定にはチーム合意が必要です。

参加者はセッション内に最大3人を登録し、その中から共同曲に含める2〜3人を選ぶ案です。「選択から外す」はデータ削除ではなく、A+BとA+Cの比較音源を保持できます。「参加者を削除する」は同意撤回を含むデータ破棄操作で、その人を含む比較音源も破棄します。デモのBからCへの切替は、削除ではなく選択変更を使います。

音楽生成は個人曲をそのまま重ねるだけでなく、共通のテンポ・調性・役割で共同編曲することを目指します。最低限どの特徴が共同曲にも残ればよいかはG3で決定します。

## 3. 利用フローと画面状態

1. 説明・同意：画像の用途、処理先、保持・削除方針を示し、本人の指紋だけを入力してもらう。拒否時は撮影・送信しない。
2. 参加者追加：匿名のA/B/Cを割り当て、カメラ撮影またはファイルを選択する。カメラを許可しない場合もアップロードへ進める。
3. 品質確認・抽出：処理中を表示し、成功時は取得できた特徴、失敗時は撮り直しの理由を示す。
4. 個人曲：5〜10秒の曲を生成し、参加者と対応させて再生する。
5. 共同曲：有効な2〜3人を選び、15〜30秒の曲を生成・再生する。
6. 比較：A+Bの後にA+Cを生成する。選択した参加者と実際に再生中の曲の参加者を明示する。
7. 削除・終了：参加者を削除するかセッションを終了し、対象データと曲を破棄する。

画面は「未入力／入力確認／抽出中／生成中／再生可能／失敗／削除済み」を区別します。古い結果が遅れて返った場合は、現在の参加者構成に適用しません。

## 4. 機能要件と受入基準

以下の受入基準は実装前に合意する試験案です。合格実績を示すものではありません。

| ID・優先度 | 要件 | 受入基準・確認方法 |
| --- | --- | --- |
| F01 Must | 説明と同意 | 同意前・拒否時に画像の取得・送信が起きない。同意撤回で参加者削除へ進める。処理先・保持期間の表示が実装と一致する |
| F02 Must | スマホ撮影・アップロード | 合意した対象端末で撮影とJPEG/PNGアップロードを各1回完了。権限拒否時はアップロードに切替可能。破損・非対応・上限超過は説明付きで拒否する。上限案10MB、確定はG1 |
| F03 Must | 品質判定と特徴抽出 | 合意した良好サンプルから最低2種類の視覚特徴を抽出。暗い・ぼけた・模様のない各サンプルでは低品質または抽出不可を通知し、成功に見せない。取得できない値を0として捏造しない |
| F04 Must | 個人曲生成 | 有効な特徴から5〜10秒の再生可能な曲を出力。入力参加者・特徴版・生成方式を結果と結び付け、画像未入力では実測由来の曲として生成しない |
| F05 Must | 共同曲生成 | 有効な2人と3人で各1曲、15〜30秒の音源を生成。1人以下では共同生成を案内付きで無効化。選択した全員のモチーフまたは音楽要素が編曲データに含まれる |
| F06 Must | 再生・停止 | 明示的な操作で再生し、停止できる。個人曲・共同曲の切替時に旧曲が重なって再生されない。再生拒否・デコード失敗を通知して再試行できる |
| F07 Must | 参加者の追加・入替・削除 | A+BからA+Cへ変更でき、生成結果にBが含まれずCが含まれる。変更前の曲は「以前の組み合わせ」と表示し、新曲と誤認させない。削除した人を含む旧曲は破棄する |
| F08 Must | 再生成と非同期整合性 | 同一構成の再生成が可能。二重操作を抑止し、生成中の入替・削除後に旧リクエストが完了しても採用しない。再生成を同じ曲にするか別アレンジにするかはG3で決定 |
| F09 Must | 失敗・待機・復旧 | 品質不足、通信失敗、タイムアウト、生成失敗を区別して撮り直し／再試行／中止へ進める。失敗時に架空の成功結果へ切替えない。待機上限案60秒、超過時は再試行を提示 |
| F10 Must | データ削除 | 参加者削除で画像・特徴・個人曲・その人を含む共同曲が再取得できなくなる。終了時は全対象を破棄。保持場所一覧と照合し、アプリログにも元画像・特徴値が残らないことを確認 |
| F11 Must | 実測とサンプルの区別 | サンプル体験を用意する場合、入力から再生まで常時「サンプル」と表示。画像解析失敗を実測成功と表示しない。ルールベースへの切替時も生成方式を表示 |
| F12 Should | 特徴・音の可視化 | 少なくとも2特徴について値または段階と音への対応を表示。推定値・抽出不可を区別し、本人識別や性格推定と解釈させない |
| F13 Should | 比較の支援 | A+BとA+Cの参加者構成・生成方式を見ながら切替試聴できる。音量・テンポ等の比較条件を揃える案をG3で決める。参加者削除後は該当する比較音源を残さない |

F05/F07の音楽的な成功はデータ上の差だけでは不十分です。G3で合意した3組の組み合わせを試聴し、「参加者変更が聴き分けられる」「Aに割り当てた要素を両曲で確認できる」をチームで確認します。主観評価の人数・方法は記録し、一般的な有効性は断言しません。

## 5. 指紋特徴と音楽生成の検証方針

スマホ撮影で必要な指紋模様を安定して取得できるかは未実証です。渦、曲線、密度、分岐は候補であり、特に細かな分岐点の抽出を現段階のMustにしません。G1で再現可能な特徴を選び、方向分布や画像内の模様の密度など粗い視覚特徴への縮小も検討します。その場合は「画像の視覚特徴からの作曲」と正確に説明します。

撮影ガイド案：指先を大きく写す、明るさを確保する、ピントを合わせる、反射を避ける。特徴の正規化・品質しきい値・左右反転や回転の扱いは画像担当が検証後に定義します。

| 方式案 | AIの役割・出力 | 利点の仮説 | 未確認事項・失敗時 |
| --- | --- | --- | --- |
| A：ルールベース | 特徴を音高・リズム・楽器などに対応付け、MIDI等から音源化 | 入力の寄与と再現条件を説明しやすい | 音楽的品質、Google技術を中核に置く条件との適合を要確認 |
| B：構造生成AI＋音源化 | 特徴と固定モチーフを渡し、音楽構造JSONを生成。検証後にMIDI/WAV等へ変換 | 個人要素を制約として共同編曲に反映できる可能性 | 利用可能モデル、JSON制約遵守、料金、待ち時間、利用条件を確認。不正出力は再試行または明示したAへ |
| C：直接音声生成 | 特徴に応じた指示から音声を得る候補 | 音色や表現の幅が広がる可能性 | 音楽生成の提供可否、アクセス権、制御性、長さ、利用条件が未確認。利用可能と仮定しない |

**選定保留**：Bを検証候補、Aを比較・フォールバック候補、Cを調査候補とする提案です。LLMが音楽・音声を直接生成できるとは断定しません。Aへ切り替えてもGoogle中核要件を満たすかを再評価し、満たさない案を提出仕様として確定しません。

再現性は「同じ画像・特徴・方式版・seedで同じ構造を得る」と「同じ指を撮り直して似た曲になる」を別々に検証します。前者も方式次第で未保証、後者は未検証です。特徴と音楽要素の対応、乱数、モデル版、アレンジ差を分けて記録します。

## 6. データ取扱い・非機能要件（提案）

指紋画像と派生特徴をセンシティブな入力として扱います。以下は設計提案で、実際の保持・削除仕様をG2で確定するまで「保存しない」「完全に削除する」と利用者に保証しません。

| ID | 提案・検証事項 |
| --- | --- |
| N01 | 元画像は抽出の一時処理だけに利用し、成功・失敗・中止いずれでも解放する。画像・特徴をDB、ファイル、アクセスログ、例外ログ、解析サービスへ永続保存しない。クラウド・外部APIの保持条件も確認する |
| N02 | 特徴・音楽構造・音源はセッション限りの一時データにする。保持上限案は最終操作から30分、参加者削除・終了時は即時破棄。ブラウザ終了だけに依存せずサーバー側も期限切れにする。外部サービスの削除可否は別途確認 |
| N03 | 可能なら端末内で特徴抽出し、外部には粗い特徴だけ送る案を比較。Python/OpenCVをサーバーで使う案では画像送信が必要なため、同意文・処理先・削除経路を変更する |
| N04 | セッションを分離し、他セッションのデータや音源を取得できない。認証情報はクライアント・公開Git・ログへ出さない。通信方式とアクセス制御を担当が確認する |
| N05 | 個人曲・共同曲それぞれの所要時間を対象端末・回線で測定する。暫定目標は各30秒以内、待機上限60秒。未達なら方式かスコープを見直し、測定条件と失敗率を残す |
| N06 | 最低限の対応端末・ブラウザはチーム所有のスマートフォン実機でG1時に確定。撮影・選択・再生を実機検証し、未確認端末の動作を保証しない |
| N07 | 入力サイズ・参加人数・同時生成数・再試行数に上限を設ける。暫定で1セッション1生成、再試行1回。料金上限と運営クレジットの範囲はG2で合意し、無制限の呼出しを避ける |

保存・共有を追加する場合は音源にも本人由来の情報が残り得る前提で、同意・保持期間・公開範囲・削除方法を改めて定義します。Must完了前には追加しません。

## 7. 概念データ契約と担当境界

以下は実装形式を固定しない契約案です。コード・API雛形ではありません。全処理はsessionId、requestId、参加者構成のrevisionで対応付けます。実名・指紋による本人IDは使用しません。

| 概念 | 必要な情報 | 受け渡し・制約 |
| --- | --- | --- |
| Session | 一時ID、同意状態、期限、参加者一覧、revision | UI↔バックエンド。匿名参加者A〜Cと本人の対応はセッション内だけ |
| ImageInput | participantId、画像、形式・サイズ、実測/サンプル区分 | UI→画像担当。実際の転送先はN03で選定。解析後は画像を返さない |
| FeatureResult | 品質状態、特徴名・値・範囲・単位、取得不可の理由、抽出版 | 画像→作曲。採用特徴と正規化はG1で固定。取得不可は明示し、0で代用しない |
| PersonalMusic | participantId、特徴版、モチーフ/構造、方式版、seed、長さ、音源参照 | 作曲→バックエンド→UI。5〜10秒。音源参照の寿命はセッション内 |
| EnsembleRequest | 有効な2〜3人のID、各モチーフ、revision、アレンジ条件 | UI/バックエンド→作曲。削除済みIDと古いrevisionは拒否 |
| EnsembleResult | 参加者ID、revision、各人の寄与対応、構造、方式、長さ、音源参照 | 作曲→UI。15〜30秒。再生対象と表示参加者を一致させる |
| Failure/Deletion | 対象ID、理由区分、再試行可否、削除対象・完了状態 | 全担当で共通化。失敗の詳細ログに画像・特徴・秘密情報を含めない |

音楽構造を採用する場合の項目候補はテンポ、拍子、調性、音符の音高・開始・長さ、楽器、参加者ごとのトラックです。値域・総尺・欠損時の扱いを検証し、不正な生成結果をそのまま音源化しません。比較用の過去曲も参加者削除の対象です。

## 8. 技術・運営要件

候補はReact/Next.js、OpenCV/Python、MIDI/生成AI、FastAPI、Cloud Runです。採用は未確定で、チーム経験・実機対応・生成品質・費用・締切を比較して決めます。

運営要件として、指定されたGoogle実行基盤の使用、Google技術を作品の中核に置くこと、選定理由の説明、利用する著作物の記録を満たす必要があります。指定基盤の具体的な対象と利用可能サービスは運営案内で再確認します。Cloud Runは候補であり、ホストするだけで中核要件を満たすとは判断しません。

| 提出前に記録する項目 | 記録内容 |
| --- | --- |
| Google技術 | 採用サービス、担当する機能、作品に必要な理由、代案との比較、運営条件との対応 |
| 外部著作物・依存物 | 音源・楽器素材・画像・ライブラリ等の名称、出典、ライセンス、用途、必要な表示。生成物の利用条件も確認 |
| デモ | 実測入力かサンプルか、生成方式、未実装範囲、失敗時の案内 |
| 最終提出 | 公開repoに必要成果物・説明・稼働URLを反映。秘密情報・指紋画像・特徴ログを含めない |

提出用リポジトリではGitHub Actions/Pagesを利用できません。開発用リポジトリの選択・新設は別の判断とし、本書作成では実施しません。

## 9. 4人の担当と依存順（割当案）

| 担当 | 主な責任 | 他担当へ渡すもの | 完了確認 |
| --- | --- | --- | --- |
| A：UI/UX | 同意、撮影、品質案内、参加者操作、再生・比較 | 画面状態、入力条件、実機検証結果 | F01/F02/F06/F07/F11/F12/F13 |
| B：画像認識 | 撮影品質、特徴の選定・抽出、画像の破棄 | FeatureResult、品質失敗例、取得限界 | F03、N01/N03の画像部分 |
| C：作曲 | 個人・共同曲、特徴対応、音源化、AI/代替方式 | 音楽構造、音源、寄与対応、方式別測定 | F04/F05/F08、G3 |
| D：バックエンド | セッション、処理接続、削除、実行基盤、提出確認 | データ契約、エラー区分、接続先、期限管理 | F09/F10、N02/N04/N05/N07 |

実名との対応と最終割当はチーム内で確認します。レビューはA↔D、B↔Cを提案します。統合とデモは全員で実施します。

依存順は「同意・保持方針と契約の合意 → 画像の取得可能性と生成方式をそれぞれ検証 → 個人曲を接続 → 共同曲と参加者変更 → 実機・削除・エラー検証」です。UIは明示したサンプルで並行検討できますが、実測の完成扱いにはしません。
